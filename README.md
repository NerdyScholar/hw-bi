# Проектирование Data Warehouse для компании "ЭлектроМир"

## 1. Бизнес-требования и цели создания Data Warehouse

**Компания:** "ЭлектроМир" - розничная сеть (онлайн и офлайн) по продаже электроники и бытовой техники.

**Цели создания Data Warehouse (DWH):**

1. Предоставление руководству консолидированной и достоверной информации для анализа бизнес-показателей и планирования развития.
2. Анализ поведения клиентов, сегментация аудитории, оценка ROI маркетинговых активностей.
3. Прогнозирование спроса, выявление неликвидных товаров, оптимизация поставок между складами.
4. Персонализация предложений, анализ истории покупок, выявление VIP-клиентов.
5. Оценка работы продавцов, магазинов, каналов продаж (онлайн/офлайн).
6. Выявление узких мест в бизнес-процессах.

**Бизнес-требования (ключевые вопросы, на которые DWH должен давать ответы):**

*   Какова динамика продаж по различным категориям товаров, брендам, регионам во времени (день, неделя, месяц, квартал, год)?
*   Какие товары являются наиболее и наименее прибыльными/продаваемыми?
*   Каков средний чек клиента? Как он меняется во времени и в зависимости от сегмента клиента?
*   Какова эффективность различных маркетинговых каналов привлечения клиентов?
*   Каков портрет нашего типичного клиента? Какие сегменты клиентов существуют?
*   Как распределяются остатки товаров по складам? Какова оборачиваемость товаров на складах?
*   Какие товары чаще всего покупают вместе (анализ потребительской корзины)?
*   Как изменились продажи после проведения определенной промо-акции?
*   Какова эффективность работы отдельных продавцов/магазинов?

## 2. Системы-источники данных

1.  **E-commerce Platform:**

    *   **Формат передачи:** **JSON** (API-выгрузка или потоковая передача).
    *   *Пример фрагмента данных:*

    *   **Данные:** Подробная информация о клиентах, история взаимодействий (звонки, встречи - если есть), сегментация клиентов, подписки на рассылки.

## 3. Модель данных для Data Warehouse (DDS слой)

Взял за основу "звезду":

**Измерения (Dimensions):**

1.  **DimDate (Измерение Дат):**
    *   `DateKey` (PK, Surrogate Key)
    *   `FullDate` (DATE) - Полная дата (e.g., 2023-10-26)
    *   `Year` (INT) - Год
    *   `Quarter` (INT) - Квартал (1-4)
    *   `Month` (INT) - Месяц (1-12)
    *   `MonthName` (VARCHAR) - Название месяца (e.g., Октябрь)
    *   `DayOfMonth` (INT) - День месяца (1-31)
    *   `DayOfWeek` (INT) - День недели (1-7, где 1 - Понедельник)
    *   `WeekOfYear` (INT) - Неделя в году
    *   `IsWeekend` (BOOLEAN) - Является ли выходным
    *   ... другие атрибуты времени

2.  **DimCustomer (Измерение Клиентов):**
    *   `CustomerKey` (PK, Surrogate Key)
    *   `CustomerID_Source` (VARCHAR) - ID клиента из системы-источника (e.g., CUST001)
    *   `FirstName` (VARCHAR) - Имя
    *   `LastName` (VARCHAR) - Фамилия
    *   `FullName` (VARCHAR) - Полное имя
    *   `Email` (VARCHAR) - Email
    *   `PhoneNumber` (VARCHAR) - Телефон
    *   `City` (VARCHAR) - Город
    *   `Country` (VARCHAR) - Страна
    *   `RegistrationDate` (DATE) - Дата регистрации
    *   `LoyaltyTier` (VARCHAR) - Уровень лояльности (e.g., Bronze, Silver, Gold)
    *   `Gender` (VARCHAR) - Пол
    *   `BirthDate` (DATE) - Дата рождения
    *   `Age` (INT) - Возраст (может вычисляться или обновляться периодически)
    *   `ValidFrom` (DATETIME) - Для SCD Type 2 (начало действия записи)
    *   `ValidTo` (DATETIME) - Для SCD Type 2 (конец действия записи)
    *   `IsCurrent` (BOOLEAN) - Для SCD Type 2 (текущая запись)

3.  **DimProduct (Измерение Продуктов):**
    *   `ProductKey` (PK, Surrogate Key)
    *   `ProductID_Source` (VARCHAR) - ID продукта из системы-источника
    *   `ProductName` (VARCHAR) - Наименование продукта
    *   `Category` (VARCHAR) - Категория
    *   `SubCategory` (VARCHAR) - Подкатегория 
    *   `Brand` (VARCHAR) - Бренд
    *   `SupplierName` (VARCHAR) - Поставщик
    *   `CostPrice` (DECIMAL) - Закупочная цена 
    *   `Color` (VARCHAR) - Цвет
    *   `Size` (VARCHAR) - Размер/Объем
    *   `ValidFrom` (DATETIME) - Для SCD Type 2
    *   `ValidTo` (DATETIME) - Для SCD Type 2
    *   `IsCurrent` (BOOLEAN) - Для SCD Type 2

4.  **DimWarehouse (Измерение Складов):**
    *   `WarehouseKey` (PK, Surrogate Key)
    *   `WarehouseID_Source` (VARCHAR) - ID склада из системы-источника
    *   `WarehouseName` (VARCHAR) - Название склада
    *   `City` (VARCHAR) - Город склада
    *   `Address` (VARCHAR) - Адрес склада
    *   `Region` (VARCHAR) - Регион

**Факты (Facts):**

1.  **FactSales (Факт Продаж):**
    *   `SaleID` (PK)
    *   `DateKey` (FK, references DimDate) - Ключ даты продажи
    *   `OrderDateKey` (FK, references DimDate) - Ключ даты создания заказа (если отличается от даты продажи/отгрузки)
    *   `CustomerKey` (FK, references DimCustomer) - Ключ клиента
    *   `ProductKey` (FK, references DimProduct) - Ключ продукта
    *   `WarehouseKey` (FK, references DimWarehouse) - Ключ склада отгрузки (если применимо)
    *   `OrderID_Source` (VARCHAR) - ID заказа из системы-источника (вырожденное измерение)
    *   `OrderLineID_Source` (VARCHAR) - ID строки заказа из системы-источника (вырожденное измерение)
    *   `QuantitySold` (INT) - Количество проданного товара
    *   `UnitPrice` (DECIMAL) - Цена за единицу товара на момент продажи
    *   `TotalAmount` (DECIMAL) - Общая сумма по строке (QuantitySold * UnitPrice)
    *   `DiscountAmount` (DECIMAL) - Сумма скидки по строке
    *   `NetAmount` (DECIMAL) - Итоговая сумма по строке (TotalAmount - DiscountAmount)
    *   `CostAmount` (DECIMAL) - Себестоимость проданных товаров (QuantitySold * CostPrice из DimProduct на момент продажи)
    *   `ProfitAmount` (DECIMAL) - Прибыль (NetAmount - CostAmount)

**Связи:**

*   `FactSales` связан с `DimDate` по `DateKey` (и `OrderDateKey`).
*   `FactSales` связан с `DimCustomer` по `CustomerKey`.
*   `FactSales` связан с `DimProduct` по `ProductKey`.
*   `FactSales` связан с `DimWarehouse` по `WarehouseKey`.


## 4. Принципы разложения данных по слоям (Stage - ODS - DDS - DataMart)

**ETL/ELT Процесс:** Данные проходят через несколько слоев, прежде чем стать доступными для анализа.

1.  **STAGE (Staging Area / Посадочный слой):**
    *  Первичное хранилище для данных, загруженных из систем-источников. Данные здесь максимально приближены к оригиналу.
    *   Обычно повторяет структуру источника или хранится в "сыром" виде (например, JSON файлы в Data Lake). Таблицы часто именуются с префиксом `stg_`.
    *   **Характеристики:**
        *   Кратковременное хранение (данные перезаписываются при каждой загрузке или хранится история за небольшой период).
        *   Минимальные преобразования (только необходимые для загрузки).
        *   Высокая скорость загрузки.
        *   Отсутствие интеграции между разными источниками на этом слое.
    *   **Пример:** `stg_ecom_orders`, `stg_crm_clients`, `stg_erp_products`.

2.  **ODS (Operational Data Store / Операционное хранилище данных):**
    * Интеграция данных из различных источников, очистка, нормализация, приведение к единому формату. Представляет собой "снимок" текущих или почти текущих операционных данных.
    * Часто нормализованная (3NF) или частично денормализованная. Таблицы отражают бизнес-сущности (Клиенты, Продукты, Заказы). Именование может быть `ods_`.
    *   **Характеристики:**
        *   Интегрированные данные.
        *   Очищенные и валидированные данные (проверка типов, диапазонов, удаление дубликатов).
        *   Данные готовы для загрузки в DDS или для оперативной отчетности.
        *   Может хранить историю изменений, но не оптимизирован для сложной аналитики.
        *   Приведение всех данных к единым справочникам (например, единый справочник городов).
    *   **Пример:** `ods_Customers`, `ods_Products`, `ods_Orders`, `ods_OrderItems`.

3.  **DDS (Data Warehouse Service Layer / Слой Детальных Данных / Core DWH):**
    *  Центральное хранилище DWH. Здесь данные организованы в виде многомерных моделей (звезды, снежинки) для поддержки аналитических запросов.
    *  Денормализованная (звезда) или частично денормализованная (снежинка). Содержит таблицы фактов и измерений.
    *   **Характеристики:**
        *   Историчность: хранятся все исторические данные, включая изменения (SCD).
        *   Предметно-ориентированность (например, Продажи, Запасы).
        *   Интегрированность и согласованность (конформные измерения).
        *   Стабильность: структура меняется редко.
        *   Использование суррогатных ключей для связей и управления SCD.
        *   Агрегаты могут предварительно рассчитываться для повышения производительности.
    *   **Пример:** `DimDate`, `DimCustomer`, `DimProduct`, `DimWarehouse`, `FactSales`.

4.  **DATAMART (Витрины Данных):**
    *    Специализированные подмножества данных из DDS, оптимизированные для конкретных бизнес-задач, отделов или групп пользователей.
    *    Часто еще более денормализованная или агрегированная версия данных из DDS. Может быть как реляционной таблицей, так и OLAP-кубом.
    *   **Характеристики:**
        *   Ориентация на конкретные потребности (например, витрина для отдела маркетинга с данными по клиентам и кампаниям, витрина для отдела продаж с данными по продажам и KPI).
        *   Более высокая производительность запросов для конкретных задач за счет агрегации и меньшего объема данных.
        *   Упрощенная модель данных для конечных пользователей.
        *   Могут быть как физическими (отдельные таблицы), так и логическими (представления над DDS).
    *   **Пример:** `dm_SalesAnalytics` (агрегированные продажи по месяцам/регионам), `dm_CustomerSegmentation` (данные для RFM-анализа).

**Поток данных:**
Системы-источники → **STAGE** → (ETL/ELT) → **ODS** → (ETL/ELT) → **DDS** → (ETL/ELT) → **DATAMART(s)** → BI-инструменты, отчеты, дашборды.
